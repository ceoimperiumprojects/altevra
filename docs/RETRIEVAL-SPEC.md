# Altevra Retrieval Redesign — Spec (Opus workflow, 2026-06-19)

## Verdict: enrich-before-embed
YES — but selectively, not on every chunk. Decision: enrich-before-embed ONLY for (a) db://turn and db://call_transcript chunks (verbose, low signal-density conversational text) and (b) any chunk whose trimmed length exceeds ~1200 chars OR is an oversized single-paragraph chunk (chunker.rs maybe_flush never splits a giant paragraph). Do NOT enrich already-dense objects (decisions/learnings/notes = title+body, wiki body) — raw-text BGE-M3 already chews through those fine and enrichment adds cost + hallucination risk for ~0 recall gain.

WHY raw BGE-M3 is NOT enough on the verbose lane, concretely: (1) A 2000-char rambling assistant turn embeds as ONE 1024-d vector that averages signal across filler — BGE-M3 mean/cls-pools the whole thing, so the one load-bearing sentence gets diluted. (2) MAX_CHUNKS_PER_TURN currently DROPS overflow chunks — that is silent permanent data loss; a distilled tail-summary chunk makes long turns lossless. (3) The chunker bakes only the heading line into the body — short chunks have no document-title breadcrumb, so "decided to drop it" is unanchored. (4) The acronym/cross-language gaps are structural in the lexical lane (sessions.rs drops tokens len<=2 so 'AI'/'VM'/'Q3' vanish; LIKE matching is language-literal) — only a distiller that emits expanded acronyms + sr<->en keyword variants fixes them at index time for ALL surfaces.

The form of enrichment is the Anthropic "contextual retrieval" pattern (cheap, proven +recall), NOT a replace-the-text summary: PREPEND a 1-2 line contextual header (doc title + heading breadcrumb + one-sentence gist) to the chunk text before embedding, and additionally store a compact JSON sidecar (distilled gist, expanded+bilingual keywords, 3-5 'questions this answers', resolved entities). Raw text stays the citation source untouched — the answer model NEVER sees only the summary. This makes the embed input meaning-dense WITHOUT betting retrieval on a 1B model's fidelity.

REJECTED framing: full per-chunk replacement-summary embedding (loses recall on details the summary omits) and enriching everything (wastes the always-on lane on dense objects that don't need it).

## Full BGE-M3 hybrid?
PARTIALLY — use dense + a SPARSE/lexical leg now; do NOT build ColBERT multi-vector yet.

HARD REALITY (verified in bge.rs:46): the Rust `fastembed` BGEM3 wrapper calls `model.embed(...)` which returns DENSE ONLY. Sparse lexical weights and the ColBERT token matrix are NOT exposed by fastembed. So "full BGE-M3 hybrid via fastembed" is impossible in-process today. Two honest paths:

(1) SPARSE LEG — get it WITHOUT BGE-M3's sparse head. We already have FTS5 BM25 over object_fts. The cheapest, highest-leverage "sparse" win is to feed the DISTILLED keyword set (from enrichment: expanded acronyms + sr<->en variants + entities) into a new FTS5 table `chunk_kw_fts(chunk_id UNINDEXED, keywords, entities)` and add it as a third RRF leg. This realizes BGE-M3's lexical-precision benefit (exact-term, morphology-bridged via the distiller, cross-language) using infrastructure that already exists and is always-compiled — no FlagEmbedding bridge dependency. The TRINITY design's plan to emit BGE-M3 native sparse from the :8091 llama-server bridge is a v2 option ONLY IF verified the gguf exposes the sparse head (it likely does not under llama.cpp embedding mode) — flag as UNVERIFIED, do not block on it.

(2) ColBERT MaxSim rerank — DEFER. It is the highest-precision stage in the literature (+5-15% nDCG) but (a) fastembed can't emit the token matrix, (b) storage is ~1MB/chunk f16 which dwarfs the 1024-d dense store on a decades corpus (sovereignty/disk cost), (c) it needs a new BLOB table + scoring path. The cheaper substitute that captures most of the intent-precision win: the "questions-this-answers" HyDE-reverse rerank signal from the distiller, scored against the query — near-free because it's pre-computed. Build ColBERT only after sqlite-vec migration and only for objects (decisions/learnings/wiki), n_tokens<=256, int8-quantized.

So: TRI-SIGNAL RRF = [object_fts BM25] + [distilled-keyword BM25] + [BGE-M3 dense cosine], fused via the existing N-list rrf_fuse. That is the real hybrid, buildable today, no new model dependency.

## Architecture
SYNTHESIS = EBE (enrich verbose lane) + TRINITY (3-leg RRF) + IRQE (query-side intent router, but CHEAP-GATED) + TCFG (coverage ledger + eval gate as the safety net). One backbone: hybrid_db_search becomes THE retrieval primitive for recall/ask/MCP. Discarded: ColBERT-now, NPU-as-perf, enrich-everything, fan-out-N-rewrites-by-default (amplifies the in-RAM cosine scan).

CAPTURE (unchanged): two lanes -> memory_chunks. guard_document redaction stays fail-closed, BEFORE anything. Add coverage_ledger (per-object freshness: content_sha256, vector_count, embedded_model, state in {discovered,chunked,embedded,stale,error}) generalizing embed_backfill_watermark — makes coverage an auditable % and triggers re-embed on drift. Close two gaps: repo-sweep over projects.yaml + a call_transcript adapter (drop dir -> db:// synthetic lane).

ENRICH (NEW, selective, async, off the hot path): a sibling daemon `altevra-enricher.service` reads an enricher_queue. For verbose/oversized/turn/transcript chunks only, the small local model emits {gist, keywords(expanded acronyms + sr<->en), questions[], entities(resolved vs mention dictionary)}. Store in memory_chunk_enrichment (chunk_id PK, source_checksum mirrors memory_chunks.checksum for idempotent drift-gated re-enrich). PREPEND the contextual header to the embed-input string; write keywords/entities to chunk_kw_fts. High-water (Personal/Health/Relationship) chunks MUST route through role_for_object -> LocalPrivate loopback (SI-7); if no local model is up, SKIP enrichment and embed raw-redacted (never send to cloud, never block).

EMBED (fix defects, keep 1024-d): switch worker to the dead embed_batch() over the claimed batch; remove the 1000-RPM Gemini-era rate limiter for local BGE; register enriched vectors under a distinct embed_meta tag (e.g. bge-m3-ctx, still dim=1024) so raw and enriched vectors coexist legally under the one-model-one-dim gate and migration is lane-by-lane. DUAL-mode: embed raw immediately so nothing is unsearchable while enrichment lags; re-embed enriched when the sidecar lands.

RETRIEVE + FUSE (the unification): extend hybrid_db_search to 3 legs -> rrf_fuse(&[object_fts_bm25, chunk_kw_bm25, dense_cosine], 60.0). FIX the semantic-only hole (hybrid_db.rs:96-98): the chunk->object map already exists (chunk_ids_to_object_ids); for fused ids missing from bm25_hits, do the chunk->memory_chunks.text join to produce title/snippet so vector-only and keyword-only hits actually surface. Parent-doc expansion via memory_chunks.document_id gives chunk-boundary neighbors as context (fixes no-overlap without re-embedding).

QUERY ROUTER (IRQE, but cheap-gated): a shared route_and_enrich() in altevra-brain generalizing ask.rs is_aggregate into {lookup, aggregate, entity, synthesis, temporal}. CRITICAL latency guard: a trivial-query pre-filter (<=2 tokens, pure entity name, or query-hash cache hit) SKIPS the LLM entirely and goes straight to hybrid_db_search — so the common case pays ZERO LLM tax. Only ambiguous/aggregate/cross-language/personal queries pay one ~256-tok local call. Fail-open to today's pipeline if the model is down or JSON fails. aggregate gets window+group_by (vs brittle phrase list); cross-language sr<->en moves local (off ask.rs's fragile cloud Haiku). Keep is_aggregate as a deterministic override floor.

RERANK (the precision stage, gated): default = the HyDE-reverse signal (query vs pre-computed 'questions this answers', pure scoring, near-free). Escalate to a local listwise MoE rerank ONLY when top-2 fused scores are within a margin OR the query is high-water (must stay local). Skip on budget pressure -> RRF order stands. Fills the named-but-unused reranker role.

ANSWER (unchanged): fused+reranked top-K + parent context -> Haiku (lookup) / Sonnet (aggregate) / Opus (huge-ask synth) with citations.

WIRE EVERYWHERE: recall (replace recency-concat merge with hybrid_db_search+RRF; recency becomes a decay tiebreak, not primary sort), ask (repoint run_lookup's per-variant retrieval at hybrid_db_search; window/group_by from router), MCP search_turns/search_files (hybrid behind mandatory ExposureGate; search_files keeps its no-redaction exception per 2026-06-18), get_context_packet (add gated dense+sparse leg so session-bootstrap finally carries semantic recall), and kill search_memory's O(vault) per-call re-scan -> read the persistent DB.

EVAL GATE (TCFG, the discipline): extend golden_eval.rs into recall@k / precision@k / MRR / faithfulness + the existing leak-suite (must stay 0). `altevra eval gate` blocks any chunking/enrich/embed/fuse/rerank change that regresses recall@10 or faithfulness or breaks the leak suite. Run BOTH CLI (ungated) and MCP (gated) profiles so we don't fix CLI while MCP silently withholds.

## NPU / MoE workload
HONEST VERDICT GROUNDED IN THE MEASURED DATA: nothing latency-sensitive runs on the XDNA1 NPU. FINAL-REPORT.md proves it is 10-13x SLOWER and 10-12x LESS efficient than the Radeon 780M iGPU for both embedding and LLM prefill, dominated by a ~2.4ms/dispatch floor + CPU-side glue (int8 quant, buffer sync, CPU fallback for norms/attention/softmax). Token-by-token autoregressive generation — exactly what a small MoE does for enrichment/rerank/expansion — is the NPU's WORST case (tiny sequential matmuls). Two models contending for accel0 (the bge server already claims 2 tile slots) will not parallelize usefully. Designing the always-on MoE FOR the NPU would turn every quality win into a throughput regression. This idea is explicitly REJECTED on the data.

WHERE THE ALWAYS-ON SMALL MODEL ACTUALLY LIVES: iGPU via llama-server Vulkan (-ngl 99) when idle, CPU (16 threads) fallback when Pavle is gaming (iGPU contention) — both on loopback openai_compat so SI-7 holds. First operational fix: `ollama serve` / llama-server as a systemd user unit, because TODAY it is STOPPED and local_private silently degrades to noop — every high-water/personal enrichment is being skipped right now.

WHAT RUNS CONTINUOUSLY (all cheap, local, idle-priority, the always-on lane busy beside the embedder): (1) ENRICH-BEFORE-EMBED contextual headers + turn/transcript-overflow distillation — the highest-value continuous job, gated to verbose chunks only, batched 4-8 prompts/request. (2) AUTO-CATEGORIZE new notes/turns into the living taxonomy + propose new categories. (3) RELEVANCE GATE scoring research candidates ('useful for an active goal?' — no Minecraft modpacks) before any research fires. (4) Initial corpus BACKFILL drain (one-shot, off-hours). Query-time ops (router classify, sr<->en expansion, listwise rerank) are NOT continuous — 1-2 calls per interactive query only, cheap-gated so trivial queries skip them.

THE NPU's HONEST JOB: keep it OFF the critical path. It runs the slow, non-urgent BULK re-embed backlog (stale rows from coverage_ledger) overnight, so the fast iGPU/CPU lane stays free for live ops. Its real value is the building-in-public / portfolio story (a working XDNA1 native inference path is genuinely rare), not throughput. Also fix the mislabel: serve_bge_npu.sh runs -ngl 0 --device none = CPU, not NPU — either flip bge to iGPU Vulkan (10x faster) or be honest that it's the CPU lane.

MODEL FOR THE HOT LOOP: llama-3.2-1b-instruct.Q8_0 (1.3GB, already pulled) — NOT lfm2.5:8b. RAM is tight (~3GiB free) and 1B alongside bge (1.1GB) + the brain daemon fits; 8B (5GB) thrashes. Keep lfm2.5:8b ONLY for occasional heavier private reasoning, never the per-chunk loop.

## Model choice
Hot always-on loop (enrich/categorize/relevance-gate, and query-time classify/expand/rerank): llama-3.2-1b-instruct.Q8_0 — already on disk, 1.3GB, fits the tight ~3GiB-free budget alongside the bge server + brain daemon, fast prefill (~1865 tok/s measured on iGPU), and these are short structured-JSON tasks where a 1B is sufficient and a 8B is wasteful + memory-dangerous. lfm2.5:8b stays as local_private for occasional heavier private reasoning (synthesis over sensitive data), invoked on-demand only — NOT in any per-chunk or per-query hot path.

Is there a BETTER small model than lfm2.5:8b? UNVERIFIED on this box and therefore not a build dependency: Qwen3-MoE-30B-A3B / Granite-4-MoE / LFM2-1.2B are candidates that, on paper, give MoE active-param efficiency, but NONE are pulled or benchmarked here. Recommendation: ship with llama-3.2-1b NOW (zero new download, proven local), and run a SEPARATE benchmark task (reuse the FINAL-REPORT methodology: tok/s, faithfulness on the golden set, RAM resident) before swapping. Do not block the spec on an unverified model claim. If a 1-3B MoE later benchmarks faster AND fits RAM, swap it in via the openai_compat config — it's a config + provider-registration change, not new architecture (factory.rs:82 pattern).

Embedding model: BGE-M3, 1024-dim, NON-NEGOTIABLE — the entire vector store + dim-gate is built on it; any change triggers a full re-embed. Served on iGPU Vulkan (10x the current CPU path) or the existing import-vectors JSONL bridge.

## Tradeoffs
ADVERSARIAL FLAGS — the real risks, not the comfortable ones:

1. NPU CAPACITY IS A TRAP, NOT A RESOURCE. The premise 'small MoE as busy as the embedder on the NPU' is killed by the measured 10-13x slowdown + 2.4ms/dispatch floor. Embed + MoE concurrently on accel0 is infeasible (limited slots, serialized dispatch). The spec routes the MoE to iGPU/CPU and leaves NPU for non-urgent bulk re-embed. If anyone 'optimizes' by moving generation back to the NPU, the eval latency gate must catch it.

2. iGPU CONTENTION WITH GAMING is a genuine conflict — the 780M is both the fast model lane AND Pavle's GPU. Mitigation (CPU fallback when iGPU busy + idle-priority) degrades throughput, not correctness; but a long enrichment backlog during a gaming session WILL lag. Accept: enrichment is async and dual-mode (raw embed happens immediately), so nothing is unsearchable — only the enriched re-embed waits.

3. RAM CEILING IS THE HARDEST CONSTRAINT (~3GiB free now). 1B model (1.3GB) + bge server (1.1GB) + brain daemon barely fits; lfm2.5:8b (5GB) does NOT co-reside. This is why the hot loop is 1B-only and 8B is on-demand. If the box stays at 3GiB free under load, even 1B + bge may pressure — monitor RSS, consider unloading bge during heavy enrichment bursts.

4. ENRICHMENT BACKLOG STARVATION: distillation is slower than raw ingest, so enricher_queue lags embedder_queue. Dual-mode (embed raw immediately, re-embed enriched later) is the mitigation but it means TWO embed passes per enriched chunk — extra compute. Initial corpus backfill is a big one-shot job; run off-hours.

5. 1B HALLUCINATION POISONING THE INDEX: a 1B inventing keywords/entities corrupts retrieval. Mitigations: entities rejected if not in the mention dictionary; raw text is always the citation source (answer model never sees only the summary); strict JSON schema + parse-fail -> fall back to raw embed; faithfulness eval blocks regressions. Still, accept residual risk — re-enrich when the model improves (enricher_model stored for audit).

6. IN-RAM COSINE SCAN IS THE LATENCY WALL. search_by_vector loads ALL model+dim vectors into RAM and scans linearly per query (~100k ceiling). The query router's fan-out (if used) multiplies this Nx — which is WHY the spec cheap-gates the router and caps rewrites. This makes sqlite-vec/HNSW a near-term dependency at scale; coverage_ledger.chunk_count tells us exactly when, instead of guessing.

7. CLI vs MCP EXPOSURE PARITY: recall (CLI, ungated) and MCP (gated) return DIFFERENT sets for the same query — the stated whole point (universal AI integration, personal-first parity) means high-water objects are invisible to the AI tools that need them. This is an intentional policy decision, not a bug; but the eval MUST run both profiles or we 'fix' CLI recall while MCP silently withholds.

8. COMPLEXITY CREEP: this synthesis touches 6 surfaces + 4 new tables + 2 daemons + an eval harness. The discipline that keeps it sane: Phase 1 is pure wiring of EXISTING code (hybrid_db_search, rrf_fuse, embed_batch) — ship that and measure before building enrichment. Everything additive (new tables never touch the 1024-dim embed_meta gate). Eval gate built early so each phase is verified, not assumed. Per CLAUDE.md §9: small verified steps > big unverified migration.

9. JSON-parse fragility of the local model: structured-output from a 1B is less reliable than Haiku. Fail-open to today's pipeline on every LLM step (enrich, route, rerank) is mandatory — the system must never get WORSE than current behavior when the local model misbehaves or is down."

2. PHASE 1 — Wire the hybrid backbone (HIGHEST LEVERAGE, mostly wiring existing code): (a) Fix hybrid_db_search semantic-only hole (hybrid_db.rs:96-98) via the chunk->memory_chunks.text join for ids missing from bm25_hits. (b) Repoint recall (kill recency-concat merge recall.rs:260), ask run_lookup, and MCP search_turns/search_files at hybrid_db_search. (c) Switch worker from embed() to embed_batch(); remove the 1000-RPM rate limiter for local BGE. This alone gives real lexical+dense fusion across all surfaces + a multi-x embed speedup at ~zero risk. Gate behind the eval harness from Phase 5.

Benchmark candidate small MoE models (Qwen3-MoE/Granite-4/LFM2-1.2B) before any swap.
